═══════════════════════════════════════════════════════════════════════════════════
COURSE CATALOG INGESTION ENGINE — DOCUMENT TO DATABASE, FULLY AUTOMATIC
═══════════════════════════════════════════════════════════════════════════════════

The system must be able to accept any academic document — scanned PDF, CamScan
output, Adobe Scan output, digital PDF, image, or spreadsheet — and automatically
extract, parse, validate, and populate the course catalog into the database.

No manual data entry. No hardcoded field names. No hardcoded degree types.
No hardcoded semester counts. No hardcoded credit hour formats.
Everything is inferred from the document and validated against tenant config.

The engine works for any university, any degree program, any document format.
It does not assume Pakistani universities. It does not assume English.
It does not assume any specific column names, layouts, or structures.

═══════════════════════════════════════════════════════════════════════════════════
WHAT THE ENGINE MUST HANDLE
═══════════════════════════════════════════════════════════════════════════════════

DOCUMENT TYPES (all must work):
  → Scanned PDFs (CamScan, Adobe Scan, phone camera) — OCR required
  → Digital PDFs (text-selectable) — direct text extraction
  → Images (JPG, PNG, WEBP, HEIC) — OCR required
  → Excel / CSV / Google Sheets exports — direct parse
  → Word documents (.docx) — direct parse
  → Mixed documents (some pages scanned, some digital) — hybrid approach

DOCUMENT CONTENT (all variations must be handled):
  → Single degree program per document
  → Multiple degree programs per document
  → Single semester per page
  → Multiple semesters per page
  → Tables with headers in any language
  → Tables without explicit headers (infer from position and content)
  → Handwritten annotations on scanned documents (flag for review)
  → Strikethrough text indicating removed courses (detect and flag as removed)
  → Checkmarks or annotations indicating changes (detect and flag)
  → Rotated pages
  → Low quality scans
  → Multi-column layouts
  → Merged cells in tables
  → Footnotes and annotations

═══════════════════════════════════════════════════════════════════════════════════
INGESTION PIPELINE — STEP BY STEP
═══════════════════════════════════════════════════════════════════════════════════

STEP 1 — DOCUMENT RECEPTION
  Accept document via:
    → Direct upload (UI drag-and-drop or file picker)
    → API endpoint (POST /api/catalog/ingest)
    → Email attachment (if email ingestion is enabled in tenantConfig)
    → URL (fetch from external source if tenantConfig.ingestion.urlEnabled = true)

  On receipt:
    → Store original document in object storage immediately (never process original)
    → Generate ingestionJobId (UUID)
    → Create IngestionJob record in database with status = 'received'
    → Return ingestionJobId to caller immediately — processing is async
    → Notify relevant role via tenantConfig.ingestion.notifyRoleId on job start

STEP 2 — DOCUMENT CLASSIFICATION
  Determine document type:
    → Check MIME type
    → Check file extension
    → Check first bytes (magic bytes) — do not trust MIME type alone
    → If PDF: determine if text-selectable or scanned
      (attempt text extraction — if result < tenantConfig.ingestion.minTextDensity
       characters per page, treat as scanned)
    → Log classification to IngestionJob.classificationLog

STEP 3 — TEXT EXTRACTION
  Based on classification:

  DIGITAL PDF / DOCX:
    → Extract text with layout preservation (maintain table structure)
    → Extract all text layers including headers, footers, annotations
    → Preserve spatial relationships between cells

  SCANNED PDF / IMAGE:
    → Run OCR engine (configurable via tenantConfig.ingestion.ocrProvider)
    → OCR provider is pluggable: 'google_vision' | 'azure_cognitive' |
      'aws_textract' | 'tesseract' | 'custom'
    → OCR provider credentials from environment — never hardcoded
    → Request structured output (tables detected as tables, not raw text)
    → Run deskew and contrast enhancement before OCR if
      tenantConfig.ingestion.ocrPreprocess = true
    → Confidence score per character and per cell — store in extraction log

  EXCEL / CSV:
    → Parse directly — no OCR needed
    → Detect header row automatically
    → Handle merged cells by propagating values downward

  ALL TYPES:
    → Store raw extracted text in IngestionJob.rawExtraction
    → Store extraction confidence score in IngestionJob.extractionConfidence
    → If confidence < tenantConfig.ingestion.minConfidenceThreshold:
      flag for human review before proceeding

STEP 4 — STRUCTURE DETECTION
  Detect the document structure automatically:

  DEGREE PROGRAM DETECTION:
    → Scan for degree program headers using pattern matching + AI
    → Patterns: 'BS *', 'MS *', 'PhD *', 'Bachelor *', 'Master *',
      'BE *', 'BCS *', 'MCS *' — but also any pattern
      tenantConfig.ingestion.degreePatterns defines
    → Each detected program is a separate catalog import scope
    → If no program detected: flag for human review with
      t('ingestion.review.noDegreeDetected')

  SEMESTER / YEAR DETECTION:
    → Detect grouping structure: semester-based or year-based
    → Detect labels: '1st Semester', 'Semester 1', 'Year 1', 'Term 1',
      'Fall', 'Spring' — any pattern, any language
    → Map detected labels to sequence numbers (1, 2, 3...)
    → If grouping structure ambiguous: flag for review

  TABLE STRUCTURE DETECTION:
    → For each table detected:
      → Identify columns: code, title, credit hours, prerequisites, type
      → Column identification is by content pattern, not position
        (a column containing patterns like 'CS-XXX', 'HS-XXX' is a code column
         even if it's in column 3 instead of column 1)
      → Credit hour format detection:
        '3+0' | '3-0' | '3/0' | '3' | '0+1' | '2+0/2+1' — all handled
        Theory hours = first number, Lab hours = second number
        If single number: all theory, zero lab
      → Prerequisite detection:
        'None' | 'N/A' | '-' | blank = no prerequisite
        Course code = prerequisite course code
        Multiple codes = multiple prerequisites (comma or slash separated)
      → Removed course detection:
        Strikethrough text → status = 'removed'
        Text containing 'Removed' → status = 'removed'
        Greyed out rows → status = 'removed' (if colour extraction available)
      → Elective detection:
        'Domain Elective' | 'GER' | 'ESC' | 'CS-XXX' | 'HS-XXX' |
        any pattern with 'XXX' or 'Elective' → type = 'elective'
        Slot number extracted from label if present

STEP 5 — DATA NORMALISATION
  Normalise all extracted data into the CourseRecord schema:

  CourseRecord {
    ingestionJobId:     string
    tenantId:           string
    degreeProgram:      string            // as detected — no normalisation applied
    degreeProgramSlug:  string            // generated from detected name
    semesterSequence:   number            // 1-based sequence
    semesterLabel:      string            // original label as detected
    courseCode:         string            // as detected
    courseCodeNormalised: string          // uppercase, trimmed, spaces removed
    courseTitle:        string            // as detected
    courseTitleNormalised: string         // trimmed, title-cased
    creditHoursTheory:  number
    creditHoursLab:     number
    creditHoursTotal:   number            // theory + lab
    prerequisites:      string[]          // list of normalised course codes
    courseType:         string            // 'compulsory' | 'elective' | 'lab' |
                                          // 'theory' | 'project' | 'internship'
    electiveSlot:       string | null     // e.g. 'Domain Elective 1'
    status:             string            // 'active' | 'removed' | 'proposed'
    annotations:        string[]          // any handwritten or flagged annotations
    extractionConfidence: number          // 0–1 per field
    requiresReview:     boolean           // true if any field confidence < threshold
    reviewReason:       string | null     // why review is needed
  }

STEP 6 — VALIDATION
  Validate every CourseRecord before database insertion:

  STRUCTURAL VALIDATION:
    → courseCode must match tenant's course code pattern
      (pattern defined in tenantConfig.catalog.codePattern — default: /^[A-Z]{2,4}-\d{3}[A-Z]?$/)
    → creditHoursTotal must be within tenantConfig.catalog.maxCreditHoursPerCourse
    → semesterSequence must be within tenantConfig.catalog.maxSemesters
    → prerequisites must reference codes that exist OR will exist in this import batch

  PREREQUISITE CHAIN VALIDATION:
    → Build a prerequisite graph for the entire import batch
    → Detect circular prerequisites (A requires B, B requires A) → error
    → Detect orphan prerequisites (references a code not in catalog) → warning
    → Detect forward prerequisites (semester 3 course requires semester 5 course) → warning

  DUPLICATE DETECTION:
    → Check against existing catalog in database
    → If courseCode already exists:
      → Compare all fields
      → If identical: skip (idempotent import)
      → If different: flag as 'update candidate' — require explicit approval before overwrite
    → If courseCode is new: mark as 'new'

  TOTAL CREDIT HOUR VALIDATION:
    → Sum credit hours per semester
    → Compare against tenantConfig.catalog.expectedCreditHoursPerSemester range
    → If outside range: flag as warning (not error — may be intentional)
    → Sum total credit hours for degree
    → Compare against tenantConfig.catalog.expectedTotalCreditHours range

STEP 7 — REVIEW QUEUE
  Any record with requiresReview = true goes to the review queue before insertion.

  ReviewQueue item:
    → Shows original extracted image crop alongside parsed data
    → Shows confidence score per field
    → Allows reviewer to correct any field
    → Allows reviewer to approve or reject
    → Reviewer identity logged (session.userId)
    → Review decision logged to IngestionJob.reviewLog

  Auto-approve if tenantConfig.ingestion.autoApproveThreshold is set
  and extractionConfidence > autoApproveThreshold for all fields.

STEP 8 — DATABASE INSERTION
  For each approved CourseRecord:
    → Insert into courses table
    → Insert prerequisite relationships into course_prerequisites table
    → Insert into catalog_versions table (full version history — never overwrite)
    → Log insertion to IngestionJob.insertionLog

  Insertion is transactional per degree program:
    → If any insertion fails for a degree program: rollback entire program
    → Other programs in the same job are not affected

STEP 9 — COMPLETION
  On job completion:
    → Update IngestionJob.status = 'completed' | 'completed_with_warnings' | 'failed'
    → Generate ingestion report (see below)
    → Notify relevant role via tenantConfig.ingestion.notifyRoleId
    → If tenantConfig.ingestion.autoPublish = true: publish catalog immediately
    → If tenantConfig.ingestion.autoPublish = false: catalog enters 'draft' state
      pending explicit publish action

═══════════════════════════════════════════════════════════════════════════════════
INGESTION REPORT — GENERATED AFTER EVERY JOB
═══════════════════════════════════════════════════════════════════════════════════

  IngestionReport {
    jobId:                  string
    documentName:           string
    documentType:           string
    extractionConfidence:   number          // average across all fields
    processingTimeMs:       number

    summary: {
      degreeProgramsDetected:   number
      semestersDetected:        number
      coursesExtracted:         number
      coursesInserted:          number
      coursesUpdated:           number
      coursesSkipped:           number      // identical duplicates
      coursesRemoved:           number      // detected as removed in document
      coursesRequiringReview:   number
      prerequisiteWarnings:     number
      creditHourWarnings:       number
      errors:                   number
    }

    perDegreeProgram: [
      {
        programName:        string
        semesterCount:      number
        courseCount:        number
        totalCreditHours:   number
        warnings:           Warning[]
        errors:             Error[]
      }
    ]

    reviewItems:      ReviewItem[]         // items needing human review
    warnings:         Warning[]            // non-blocking issues
    errors:           Error[]              // blocking issues

    rawExtractionStorageUrl:  string       // link to stored raw extraction
    originalDocumentUrl:      string       // link to original document
  }

═══════════════════════════════════════════════════════════════════════════════════
COURSE CATALOG DATA MODEL — FULLY DYNAMIC
═══════════════════════════════════════════════════════════════════════════════════

DegreeProgram {
  id:                   string            // UUID
  tenantId:             string
  name:                 string            // e.g. 'BS Computer Science'
  slug:                 string            // e.g. 'bs-computer-science'
  level:                string            // resolved from tenantConfig.catalog.degreeLevels
                                          // e.g. 'bachelors' | 'masters' | 'phd' | 'diploma'
  durationSemesters:    number            // total semesters — from config or inferred
  totalCreditHours:     number            // from catalog or tenantConfig
  batch:                string | null     // e.g. '2023F' — extracted from document if present
  status:               string            // 'draft' | 'active' | 'archived'
  effectiveFrom:        date | null
  effectiveTo:          date | null
  catalogVersion:       number            // auto-incremented on each import
  sourceDocumentUrl:    string | null     // original document that produced this catalog
  createdAt:            timestamp
  updatedAt:            timestamp
}

Course {
  id:                   string
  tenantId:             string
  degreeProgramId:      string
  semesterSequence:     number
  semesterLabel:        string            // original label as in document
  courseCode:           string
  courseTitle:          string
  creditHoursTheory:    number
  creditHoursLab:       number
  creditHoursTotal:     number
  courseType:           string            // from tenantConfig.catalog.courseTypes
  electiveSlot:         string | null
  status:               string            // 'active' | 'removed' | 'proposed'
  catalogVersion:       number
  createdAt:            timestamp
  updatedAt:            timestamp
}

CoursePrerequisite {
  courseId:             string
  prerequisiteCourseId: string
  prerequisiteType:     string            // 'hard' | 'soft' | 'concurrent'
                                          // hard = must pass before
                                          // soft = recommended
                                          // concurrent = can take same semester
}

CatalogVersion {
  id:                   string
  tenantId:             string
  degreeProgramId:      string
  version:              number
  publishedAt:          timestamp | null
  publishedBy:          string | null     // userId
  ingestionJobId:       string | null     // which job produced this version
  snapshot:             json              // full catalog snapshot at this version
  changeLog:            json              // diff from previous version
}

DEGREE TREE — PREREQUISITE GRAPH & COURSE FLOW VISUALISATION
═══════════════════════════════════════════════════════════════════════════════════

Every degree program has a course tree — a directed graph showing:
  → Course sequence across semesters
  → Prerequisite relationships between courses
  → Elective slots and their options
  → Credit hour accumulation by semester
  → Critical path (which courses gate the most subsequent courses)

The tree is computed at catalog publish time and stored as a graph structure.
It is not recomputed on every render — it is computed once and cached.
It is recomputed when the catalog version changes.

DegreeTree {
  degreeProgramId:      string
  catalogVersion:       number
  nodes:                TreeNode[]
  edges:                TreeEdge[]
  criticalPath:         string[]          // courseIds in critical path order
  semesterLanes:        SemesterLane[]    // for visualisation
  computedAt:           timestamp
}

TreeNode {
  courseId:             string
  courseCode:           string
  courseTitle:          string
  semesterSequence:     number
  creditHoursTotal:     number
  courseType:           string
  electiveSlot:         string | null
  status:               string
  isOnCriticalPath:     boolean
  gateCount:            number            // how many courses this one gates
  depthFromRoot:        number            // how deep in the prerequisite chain
}

TreeEdge {
  fromCourseId:         string            // prerequisite
  toCourseId:           string            // course that requires it
  edgeType:             string            // 'hard' | 'soft' | 'concurrent'
}

The tree is rendered using the AegisCore chart system (NChart).
Chart type: custom DAG (directed acyclic graph) built on D3 force layout.
Zoom, hover tooltips, and accessibility apply per AegisCore chart laws.

Student's personal degree tree overlay:
  → Same tree, overlaid with student's personal progress
  → Completed courses: highlighted (colour from token system)
  → In-progress courses: highlighted differently
  → Available to take next semester: highlighted
  → Not yet available (prerequisites not met): greyed
  → Locked (prerequisite failed): marked
  → This overlay is computed per student at session time
  → Never hardcoded per degree program

MISSING CAPABILITIES — GAPS IDENTIFIED FROM DOCUMENT ANALYSIS
(Based on the uploaded BS Computer Science curriculum document)
═══════════════════════════════════════════════════════════════════════════════════

The following are capabilities that a complete system needs beyond basic
course listing. These were absent or incomplete in the reviewed document
and must be addressed in the system:

GAP 1 — ELECTIVE MANAGEMENT
  The document shows 7 Domain Elective slots (DE-1 through DE-7) and
  GER & ESC slots, but does not specify what courses can fill these slots.
  The system needs:
    → Elective slot definitions per degree program
    → Course pool per elective slot (which courses are valid options)
    → Student elective selection and approval workflow
    → Elective substitution requests and approval
    → Elective availability per semester (not all electives offered every semester)
    → Minimum/maximum elective credit hours per category

  ElectiveSlot {
    id:                 string
    degreeProgramId:    string
    slotLabel:          string            // e.g. 'Domain Elective - 1'
    slotCategory:       string            // e.g. 'domain' | 'ger' | 'esc' | 'free'
    semesterSequence:   number
    creditHoursTheory:  number
    creditHoursLab:     number
    eligibleCourseIds:  string[]          // courses that can fill this slot
    minGradeRequired:   string | null     // minimum grade in prerequisites
    isStudentChoice:    boolean           // student picks from pool
    requiresApproval:   boolean           // requires advisor approval
  }

GAP 2 — COURSE OFFERING SCHEDULE
  The document shows what courses exist but not when they are offered.
  The system needs:
    → Which courses are offered in Fall vs Spring vs Summer
    → Which courses run in which academic year
    → Capacity per offering (max students per section)
    → Multiple sections per course
    → Offering schedule per campus (multi-campus support)

  CourseOffering {
    id:                 string
    courseId:           string
    academicYear:       string
    semester:           string            // from tenantConfig — not hardcoded
    sectionNumber:      number
    capacity:           number            // from tenantConfig.catalog.defaultSectionCapacity
    enrolledCount:      number
    campusId:           string | null
    status:             string            // 'planned' | 'open' | 'closed' | 'cancelled'
  }

GAP 3 — GRADE POLICY PER COURSE
  The document does not specify grading schemes per course.
  The system needs:
    → Grading scheme per course (absolute or relative)
    → Grade boundaries (configurable per tenant, per degree, per course)
    → Pass/fail threshold per course
    → GPA contribution per course
    → Repeat policy (can a course be repeated? how many times?)
    → Grade replacement policy on repeat

  CourseGradePolicy {
    courseId:           string
    gradingScheme:      string            // from tenantConfig.grading.schemes
    passingGrade:       string            // from tenantConfig.grading.passingGrade
    gpaWeight:          number            // usually = creditHoursTotal
    canRepeat:          boolean
    maxRepeatAttempts:  number | null
    gradeReplacement:   string            // 'latest' | 'highest' | 'average'
  }

GAP 4 — COURSE EQUIVALENCY & TRANSFER CREDIT
  Students transferring from other universities need:
    → Course equivalency mapping (their course X = our course Y)
    → Transfer credit approval workflow
    → Maximum transfer credits allowed (from tenantConfig)
    → Which courses cannot be transferred (must be taken at this university)

GAP 5 — CO-REQUISITE TRACKING
  The document only shows prerequisites. The system needs:
    → Co-requisites (must be taken simultaneously)
    → Anti-requisites (cannot be taken if already taken an equivalent)
    → Advisory prerequisites (recommended but not enforced)

GAP 6 — CREDIT HOUR TYPE DIFFERENTIATION
  The document uses formats like '3+0', '0+1', '3+0/2+1'.
  The '3+0/2+1' format for electives means the credit hours vary by
  which elective course fills the slot. The system needs:
    → Variable credit hour slots
    → Credit hour validation per elective fill
    → Total credit hour recalculation when electives are selected

GAP 7 — CATALOG VERSIONING & BATCH DIFFERENTIATION
  The document is titled 'Batch 2023F to Onward'. The system needs:
    → Full version history per degree program per batch
    → Students locked to their intake's catalog version
    → Changes to catalog (added/removed courses) tracked per version
    → Grandfathering rules (can a student switch to a newer catalog?)
    → Comparison view between catalog versions

GAP 8 — COURSE ATTRIBUTE TAGGING
  The system needs courses tagged with attributes for filtering and reporting:
    → Accreditation mapping (which OBE outcomes does this course address)
    → HEC category (compulsory, general education, domain core, elective)
    → Lab requirement (does this course need a specific lab or equipment)
    → Course delivery mode (in-person, online, hybrid)
    → Language of instruction (if multilingual university)

TENANT CONFIGURATION FOR CATALOG INGESTION
═══════════════════════════════════════════════════════════════════════════════════

tenantConfig.catalog {
  codePattern:                  string      // regex for valid course codes
  degreeLevels:                 string[]    // ['bachelors', 'masters', 'phd', ...]
  courseTypes:                  string[]    // ['compulsory', 'elective', 'lab', ...]
  maxCreditHoursPerCourse:      number
  maxSemesters:                 number
  defaultSectionCapacity:       number
  expectedCreditHoursPerSemester: { min: number, max: number }
  expectedTotalCreditHours:     { min: number, max: number }
  gradingSchemes:               GradingScheme[]
  passingGrade:                 string
}

tenantConfig.ingestion {
  ocrProvider:                  string      // 'google_vision' | 'azure_cognitive' |
                                            // 'aws_textract' | 'tesseract' | 'custom'
  ocrPreprocess:                boolean
  minTextDensity:               number      // chars per page below which = scanned
  minConfidenceThreshold:       number      // 0–1
  autoApproveThreshold:         number      // 0–1
  autoPublish:                  boolean
  notifyRoleId:                 string      // which role gets notified on job events
  urlEnabled:                   boolean
  degreePatterns:               string[]    // additional regex patterns for degree detection
  maxFileSizeMb:                number
  allowedMimeTypes:             string[]
}
