A1 — Before You Begin

Everything you need to know before installing and running AegisCore for the first time.

What Is AegisCore?

AegisCore is a complete university management platform that handles everything from admissions and course scheduling to fee collection, grade management, attendance tracking, and convocation ceremonies. It runs as a web application that you can deploy on your own servers or in the cloud, giving your institution full control over student data, faculty workflows, and financial operations. Built with modern security practices and designed to scale from a single department to an entire multi-campus university system, AegisCore replaces dozens of spreadsheets and disconnected tools with one unified, easy-to-use interface. The platform is open-source software, meaning you own your data and your deployment with no vendor lock-in and no per-user licensing fees for self-hosted installations.

Pre-Installation Checklist

Before you install anything, print or bookmark this checklist and verify each item. This checklist takes about 5 minutes and prevents the most common installation failures. Check off each item as you confirm it:

  • My computer runs Ubuntu 24.04 or macOS 13+ (check: lsb_release -a on Ubuntu, Apple menu → About This Mac on macOS)
  • Docker Engine 24+ is installed (check: docker --version)
  • Docker Compose V2 is installed (check: docker compose version — must say "v2.x.x")
  • At least 8 GB RAM is available (check: free -h on Ubuntu, Activity Monitor on macOS)
  • At least 20 GB free disk space (check: df -h on Ubuntu, Apple menu → System Settings → General → Storage on macOS)
  • My internet connection is working (open a web browser and visit any website)
  • I have downloaded the AegisCore ZIP file from the official repository
  • I have extracted the ZIP to a folder named aegiscore-demo
  • I know how to open a terminal (macOS: Spotlight → "Terminal", Ubuntu: Ctrl+Alt+T)
  • Port 3000 is not in use (check: lsof -i :3000 — should return nothing)

Installation Decision Guide

Before you download anything, answer these questions to determine the best deployment path for your institution. This decision guide saves time by helping you skip steps that do not apply to your situation:

Decision 1: Demo or Production?

  • Are you evaluating AegisCore to see if it fits your needs? → Run the demo locally (Section A2). No cloud accounts needed. Takes 20-30 minutes. All features available with sample data.
  • Are you ready to deploy AegisCore for real use by your institution? → Go to production deployment (Section A3). Requires a database (cloud or on-premises) and a server. Takes 45-90 minutes.

Decision 2: Which Cloud Provider?

  • Do you have an existing relationship with Azure, AWS, or GCP? → Use that provider. Familiarity with the console and existing billing arrangements simplify setup.
  • Is this your first cloud deployment, and do you want the simplest option? → Use Supabase (recommended). The free tier is sufficient to start, and the setup is dramatically simpler than the major cloud providers.
  • Do you have regulatory requirements for on-premises data storage? → Use the LOCAL deployment model on a VPS or your own hardware. All data stays within your physical control.

Decision 3: Secrets Management

  • Is this a demo or single-server deployment? → Use "None" (environment file). Simple, adequate for single-server scenarios.
  • Are you deploying on Azure, AWS, or GCP? → Use the native secrets manager for your platform (Key Vault, Secrets Manager, or Secret Manager). Better security, easier rotation.
  • Do you need multi-cloud or self-hosted secrets management? → Use Infisical. Open source, self-hostable, works across any infrastructure.

  • Network Configuration: For cloud deployments, ensure your server can make outbound HTTPS connections on port 443.   • Docker Engine: Version 24.0 or later with Docker Compose V2 plugin. Docker Desktop includes both on macOS; on Ubuntu, install via the official Docker repository.
  • RAM: Minimum 8 GB available memory. 16 GB is strongly recommended for production deployments with more than 500 concurrent users.
  • Disk Space: At least 20 GB of free disk space for the demo environment. For production, 100 GB SSD or more is recommended, depending on the size of your institution.
  • Internet Connection: Required for the first setup to download Docker images (approximately 2 GB total) and dependencies. Subsequent starts do not require internet access.
  • Terminal Access: You need to be comfortable opening a terminal and running basic commands. No programming experience is required.
  • Web Browser: Any modern browser — Chrome 110+, Firefox 115+, Safari 16+, or Edge 110+. Mobile browsers are supported for staff and student access.

Network and Firewall Considerations

If your university operates behind a corporate firewall or proxy server, you may need to configure Docker to work within your network environment before starting the installation. Here is what you need to know:

Proxy Configuration

If your organization requires internet traffic to go through an HTTP/HTTPS proxy, Docker needs to be told about it. Create or edit the Docker daemon configuration file:

sudo mkdir -p /etc/systemd/system/docker.service.d sudo nano /etc/systemd/system/docker.service.d/http-proxy.conf

Add the following lines, replacing the proxy address with your organization's actual proxy:

[Service] Environment="HTTP_PROXY=http://proxy.youruniversity.edu:8080" Environment="HTTPS_PROXY=http://proxy.youruniversity.edu:8080" Environment="NO_PROXY=localhost,127.0.0.1,.local"

Then reload and restart Docker:

sudo systemctl daemon-reload sudo systemctl restart docker

Contact your network administrator if you are unsure about your proxy settings. Most university networks do not require proxy configuration for outbound internet access.

Required Outbound Ports

For AegisCore to function correctly, your server must be able to make outbound connections on these ports:

PortProtocolPurpose
443HTTPSDocker image registry, Let's Encrypt certificate issuance, SMTP relay (if using external SMTP)
80HTTPLet's Encrypt HTTP challenge for certificate renewal (only during renewal, every 60 days)

Inbound connections to your server need only ports 443 (HTTPS) and, if Let's Encrypt is used, port 80 (HTTP). All other inbound ports should be closed for security.

Understanding the AegisCore Architecture

Understanding the AegisCore Architecture

While you do not need to be a software engineer to deploy AegisCore, understanding the high-level architecture helps you troubleshoot problems and communicate effectively with the support team. AegisCore consists of five main components that work together:

  • Web Server (Nginx + Application): This is what users interact with. Nginx handles incoming web requests, serves static files (images, CSS, JavaScript), and forwards dynamic requests to the AegisCore application server. The application server runs the core business logic — it processes login requests, fetches student data, calculates grades, and generates reports.
  • PostgreSQL Database: The single source of truth for all data. Every student record, every grade, every fee payment, every attendance mark is stored here. PostgreSQL provides ACID-compliant transactions (meaning data is never left in a half-written state), row-level security, and robust backup capabilities.
  • Redis Cache: An in-memory data store that makes AegisCore fast. Frequently accessed data (session information, permission checks, recent query results) is cached in Redis so the application does not have to query the database for every single request. Without Redis, AegisCore would be noticeably slower, especially for pages that display large tables of data.
  • Background Worker: Handles tasks that do not need to happen immediately. When a student submits a grade appeal, the system sends an email notification — but it does not make the student wait for the email to be sent before showing the confirmation page. The worker picks up the email task from a queue and sends it in the background. Other worker tasks include generating PDF reports, processing uploaded CSV files, and running DefaultSense analytics calculations.
  • Optional Services (Enterprise Tier): NidaBot AI engine, SafeSpace counseling platform, and predictive analytics models run as separate containers that communicate with the main application through Redis message queues. If these optional services are not needed, they can be disabled in the Docker Compose configuration to reduce resource usage.

All five components run as Docker containers. Docker is a technology that packages software into standardized units called containers, ensuring that AegisCore runs the same way on your laptop, on a university server, or in the cloud. You do not need to install PostgreSQL, Redis, or Nginx separately — the Docker images include everything.

  • Perceivable: All non-text content has text alternatives. All video content includes captions. Grading Scenarios and Best Practices

Here are common grading situations faculty encounter and the recommended approach within AegisCore:

Scenario: A student was absent for the mid-term exam

Do not enter a zero. Instead, leave the marks field blank and add a note: "Absent — medical leave approved." The student's attendance record and leave approval status are automatically checked. If the leave was approved, the system marks the exam as "Excused" and the component weight is redistributed across the remaining assessments (or a make-up exam is scheduled, depending on your university's policy). If the leave was not approved, the exam is marked as "Missed" and the student receives a zero, but they can still submit a grade appeal.

Scenario: A student disputes a grade before formally appealing

You may receive a message from a student asking about a grade before they file an official appeal. It is always better to resolve grade concerns informally when possible. Review the grade, and if you find an error, correct it directly on the Grading page. Add a brief note explaining the correction. The student will see the updated grade and will not need to go through the formal appeal process. Only correct grades where there is a genuine error — do not change grades due to student pressure or negotiation, as this violates academic integrity policies.

Scenario: Entering grades for a large class (100+ students)

Use the CSV upload feature for efficiency. Download the grading template for the assessment (click "Download Template" on the Grading page). Fill in marks in Excel or Google Sheets, save as CSV, and upload. The system validates all marks against maximum possible scores and highlights any rows with errors (e.g., marks exceeding maximum, missing student IDs, duplicate entries). Fix errors and re-upload. This is much faster than entering marks one by one for large classes.

How to Read Error Messages

Before diving into specific problems, here is how to quickly find and interpret error messages:

  • Browser errors: If you see an error page or blank screen, open your browser's Developer Tools (F12 or Ctrl+Shift+I) and look at the Console tab for JavaScript errors, or the Network tab for HTTP status codes (4xx = client error, 5xx = server error).
  • Docker container errors: Run docker ps -a to see which containers are running. Any container with a status other than "Up" needs investigation. Run docker logs [container-name] --tail 100 to see the most recent log output.
  • Application errors: Check the web server logs with docker logs aegiscore-web --tail 200 | grep -iE "error|fail|exception". The worker logs with docker logs aegiscore-worker --tail 100. And the database logs with docker logs aegiscore-db --tail 50.
  • System errors: Check system logs with sudo journalctl -xe --no-pager | tail -50 (Ubuntu) or Console.app (macOS). Look for "oom," "killed," "disk," or "docker" related messages.

Always copy the exact error message when searching for solutions or contacting support. Partial or paraphrased errors make troubleshooting much harder. Screenshots are helpful, but the text of the error message is essential.

Problem 1: Port Already in Use

Error: bind: address already in use

Fix: sudo lsof -i :3000 to find the process, then sudo kill -9 [PID]. Or change the port in .env to PORT=3001.

Problem 2: Docker Not Running

Error: Cannot connect to the Docker daemon

Fix: On Ubuntu: sudo systemctl start docker. On macOS: open Docker Desktop from Applications and wait for the whale icon to stabilize.

Problem 3: Permission Denied

Error: permission denied while trying to connect to the Docker daemon socket

Fix: Add your user to the docker group: sudo usermod -aG docker $USER, then log out and log back in.

Problem 4: Out of Memory

Error: container killed by OOM or exit code 137

Fix: Close other applications. In Docker Desktop (macOS), go to Settings → Resources and increase memory to at least 6 GB. On Ubuntu, check with free -h.

Problem 5: Missing Docker Compose

Error: docker-compose: command not found

Fix: Install Docker Compose V2: sudo apt install docker-compose-v2. Remove old version: sudo apt remove docker-compose.

A3 — Production Deployment

Deploy AegisCore to a cloud provider or your own server for production use by your entire institution.

Deployment Models: LOCAL, CLOUD, and HYBRID

AegisCore supports three deployment models:

  • LOCAL (On-Premises): AegisCore runs on servers physically located at your university, in your own data center. You manage hardware, networking, and physical security. Gives you the most control but requires an in-house IT team.
  • CLOUD: AegisCore runs on a cloud provider such as Microsoft Azure, AWS, GCP, or Supabase. The cloud provider manages the physical hardware. You manage software configuration. Most popular choice — eliminates hardware maintenance and allows easy scaling.
  • HYBRID: Some services run on-premises (e.g., database in university data center) while the application server runs in the cloud. Common when institutions have existing infrastructure or regulatory requirements for on-site data storage.

Scaling Your Deployment

As your institution grows, you may need to scale AegisCore to handle more users. Here is how to approach scaling at each level of growth:

Small Institution (Up to 500 Students)

A single VPS with 4 vCPUs, 8 GB RAM, and 80 GB SSD is sufficient. Run all services (web server, database, Redis, worker) on the same machine. The Supabase free tier or a $25/month VPS from any provider works well at this scale. Docker handles all service orchestration on a single host.

Medium Institution (500–2,000 Students)

Separate the database onto its own server or use a managed database service (RDS, Cloud SQL, Supabase Pro). This prevents database queries from competing with web traffic for CPU and memory. Increase the web server to 4–8 vCPUs and 16 GB RAM. Add a second background worker process for handling increased report generation and email volume. Configure Redis with a 512 MB memory limit.

Large Institution (2,000–10,000 Students)

Deploy multiple web server containers behind a load balancer (Nginx or a cloud load balancer). Use a managed PostgreSQL service with read replicas for reporting queries. Deploy Redis in a cluster configuration for high availability. Separate the background worker into dedicated workers: one for emails, one for report generation, one for DefaultSense analytics. Consider deploying to Kubernetes for automated scaling during peak periods (exam results day, fee payment deadlines, convocation).

Enterprise / Multi-Campus (10,000+ Students)

Deploy across multiple availability zones or regions for geographic redundancy. Use a dedicated database cluster with automatic failover. Implement a content delivery network (CDN) for static assets. Set up comprehensive monitoring with Grafana dashboards and Prometheus alerting. Engage the AegisCore enterprise support team for architecture review and capacity planning (included with Enterprise license tier).

Scaling Tips

  • Database is usually the bottleneck first. Before scaling everything else, check if database query performance is the issue. Use docker logs aegiscore-db --tail 100 to check for slow queries. Add database indexes for commonly filtered columns.
  • Redis eviction policy matters. At scale, Redis can consume significant memory. Set maxmemory-policy allkeys-lru so that Redis automatically evicts old cache entries when memory fills up, rather than crashing.
  • Monitor before scaling. Do not scale based on assumptions. Use docker stats to see actual CPU and memory usage during peak hours. Scale only when you consistently exceed 70% utilization.
  • Session stickiness. If you deploy multiple web server instances, configure your load balancer for session stickiness (also called session affinity). AegisCore stores some session data in memory for performance, and requests from the same user must go to the same server or be shared via Redis.

A4 — Secrets & Security

How AegisCore handles sensitive credentials and how to configure secure secret storage.

What Is a Secret?

A secret is any piece of information that must be kept confidential — database passwords, encryption keys, API tokens, SMTP credentials. If exposed, an attacker could access your database, impersonate users, decrypt sensitive data, or send unauthorized emails. AegisCore never stores secrets in source code or version control.

Automatic Secret Generation

When you run ./scripts/bootstrap-env.sh, the script automatically generates cryptographically secure random values for: database encryption key (32 bytes), JWT signing secret (64 bytes), session encryption key, internal service authentication tokens, and API rate-limiting secret.

The .env File

The .env file lives in the root directory of your AegisCore installation. It contains all environment variables — database URLs, secrets, feature flags, service configurations — in KEY=VALUE format.

🚨
Important Never share your .env file. Never commit it to Git. Never send it over email, Slack, or WhatsApp. Never include it in screenshots. If you need to share configuration, share only the key names (without values) and let teammates fill in values from their own secure source. The .env file is automatically added to .gitignore during bootstrap.

Secret Storage Providers

Provider: None (Environment File Only)

Best for: Demo environments, single-server deployments behind a firewall, or institutions with strong physical security. All secrets stored only in the .env file. Restrict permissions:

Best for: Institutions using Microsoft Azure. Uses FIPS 140-2 Level 2 validated HSMs.

  2. Under "Access configuration," choose "Vault access policy" and grant your app's managed identity "Get" and "List" secret permissions.
  3. Create a secret in Key Vault for each .env value (e.g., DATABASE-URL).
  4. Set SECRETS_PROVIDER=azure and AZURE_KEY_VAULT_URI=https://your-vault.vault.azure.net/.
  5. Remove actual secret values from .env.

Provider: AWS Secrets Manager

Best for: Institutions on AWS. Supports automatic secret rotation.

  1. In AWS Console, navigate to Secrets Manager, click "Store a new secret," choose "Other type of secret."
  2. Enter each key-value pair from your .env file.
  3. Name it aegiscore/production.
  4. Configure automatic rotation if desired (requires Lambda).
  5. Attach IAM policy granting secretsmanager:GetSecretValue on this secret to your EC2/ECS role.
  6. Set SECRETS_PROVIDER=aws and AWS_SECRET_ARN=arn:aws:secretsmanager:region:account:secret:aegiscore/production.

Best for: Institutions wanting open-source, self-hosted secrets management across multiple cloud providers.

  2. Create a project "AegisCore" with environment "production." Add all secrets.

Tenant Data Isolation Deep Dive

Understanding how AegisCore isolates data between tenants is important for compliance and security planning. The isolation works at multiple levels:

  • Database Schema Isolation: Each tenant receives a separate PostgreSQL schema (a namespace within the database). Tables for Tenant A are stored in schema tenant_a and tables for Tenant B are stored in schema tenant_b. The application uses PostgreSQL's search_path to ensure that queries only access the current tenant's schema. This means that even if a bug in the application accidentally omitted the tenant filter, PostgreSQL would still prevent cross-tenant data access at the database level.
  • Row-Level Security (RLS): Within each tenant schema, PostgreSQL row-level security policies add an additional layer of protection. Even within a single tenant, a faculty member cannot query student financial records, and a student cannot query another student's grades. RLS policies are enforced by the database, not the application, providing defense in depth.
  • File Storage Isolation: Uploaded files (profile pictures, logos, document attachments) are stored in tenant-specific directories or buckets. A student's uploaded assignment from University A is physically stored in a different location than a student's assignment from University B.
  • Redis Key Namespacing: Cached data in Redis uses tenant-prefixed keys (e.g., tenant_a:session:xyz vs tenant_b:session:abc), ensuring that cached data cannot leak between tenants.
  • Audit Trail: Every administrative action is logged with the tenant ID, user ID, action type, timestamp, and affected records. This audit trail allows compliance officers to verify that no unauthorized cross-tenant access has occurred and to trace the source of any data changes.

This multi-layered isolation means that AegisCore is suitable for scenarios where strict data separation is required — for example, a university system with multiple affiliated colleges that must keep their academic and financial records completely separate for accreditation purposes, or a service provider that hosts AegisCore for multiple independent universities.

A7 — Backups & Recovery

How AegisCore protects your data with automated backups and how to restore if something goes wrong.

RTO and RPO — Explained in Plain Language

RTO (Recovery Time Objective): How quickly your system is back online after a failure. AegisCore targets RTO less than 60 seconds. Containers automatically restart if they crash, and health checks can trigger failover to a standby instance.

RPO (Recovery Point Objective): How much data you might lose, measured in time. AegisCore targets RPO less than 5 seconds. With synchronous replication, this approaches zero: every transaction is written to at least two servers before being confirmed.

In plain language: If your server crashes right now, AegisCore is designed so that everything is back online within about a minute, and you will have lost at most a few seconds of recent activity. Students will not lose grades. Finance will not lose payment records. Attendance marked seconds before the crash will be safely stored.

How Automatic Backups Work

  • Continuous WAL Archiving: Every database transaction is written to a Write-Ahead Log that is continuously streamed to a backup location. This provides the sub-5-second RPO.
  • Daily Full Backups: Complete database snapshot once every 24 hours, typically at 3:00 AM. Retained for 30 days.
  • Weekly Consolidated Backups: One weekly backup retained for 90 days for long-term recovery.
  • Automated Verification: Daily, the most recent backup is restored to a temporary instance and checked for integrity. If verification fails, an alert is sent to the super admin.

How to Manually Trigger a Backup

# Trigger an immediate full backup ./scripts/backup.sh --full # Trigger with a descriptive tag ./scripts/backup.sh --full --tag="Before upgrading to v2.5" # Keep this backup for 365 days ./scripts/backup.sh --full --retain 365

How to Restore from a Backup

🚨
Important Restoring from backup is irreversible. All data created after the backup was taken will be permanently lost. Before restoring: (1) Take a manual backup of current state. (2) Verify backup integrity. (3) Notify all users. (4) Test the procedure on a staging environment first. Restoring should always be your last resort.

List available backups:

./scripts/restore.sh --list

Restore the latest verified backup:

./scripts/restore.sh --latest

Restore a specific backup by date:

./scripts/restore.sh --date 2025-08-01

Point-in-time recovery (PITR):

./scripts/restore.sh --point-in-time "2025-08-01 14:30:00"

The restore process takes AegisCore offline temporarily (2–5 minutes for databases under 10 GB). Users will see a maintenance page. After restore completes, migrations run automatically and services restart.

💡
Pro tip Practice restoring from backup once per quarter — treat it as a fire drill for your data. Better to find problems during a drill than during an actual emergency. Document how long it takes and share with university leadership.

Student Troubleshooting: Common Problems and Solutions

Here are the most common issues students encounter and exactly what to do about each one. If your problem is not listed here, ask NidaBot, check the in-app help (? icon on any page), or submit a support ticket.

Problem: "I cannot see my grades for a course"

Possible causes and solutions:

  • The instructor has not posted grades yet. Grades appear as soon as the instructor submits them. Check the submission deadline for the assessment (shown on your My Grades page). If the deadline has passed and grades are still missing, contact the instructor through AegisCore's messaging system (click the envelope icon on the course page).
  • You are looking at the wrong semester. Use the semester selector dropdown at the top of the My Grades page to switch between current and past semesters.
  • You are not officially enrolled in the course. Check Academic → My Enrollments. If the course is not listed, contact your department office or registrar. You may have an enrollment issue that needs to be resolved before grades appear.

Problem: "My attendance percentage is wrong"

Possible causes and solutions:

  • The instructor has not marked recent attendance. Attendance percentages update when the instructor saves attendance. If a recent class session is not reflected in your percentage, the instructor may not have taken attendance yet or may not have saved it. Contact the instructor to confirm.
  • You were marked incorrectly. If you believe you were present but marked absent (or vice versa), contact the instructor immediately. Instructors can correct attendance records for past dates. Provide the specific date and class session. The sooner you report the error, the more likely it is to be corrected.
  • An approved leave is not reflected. If you submitted a leave request and it was approved, but your attendance percentage still shows the absence, wait 24 hours. Approved leaves should automatically update your attendance record within one day. If the update does not occur, contact the instructor.

Problem: "My fee payment is not showing in AegisCore"

Possible causes and solutions:

  • RAAST payment is still processing. RAAST payments typically reflect within 5-30 seconds. If it has been less than 5 minutes, wait and refresh the page. If more than 30 minutes, check your bank app to confirm the payment was successful (amount deducted).
  • Wrong RAAST payment ID entered. Even one wrong digit in the 12-digit payment ID will send the payment elsewhere. Check the payment ID on your AegisCore fee page against the ID you entered in your bank app. Contact the finance office with your bank confirmation and transaction reference number.
  • Payment was made via a method that requires manual processing. Bank transfers, cheques, and cash payments must be manually recorded by finance staff. These methods can take 1-3 working days to appear in AegisCore. Contact the finance office to confirm receipt.

Problem: "NidaBot does not understand my accent / pronunciation"

Solutions:

  • Use text mode. When NidaBot is open, click the keyboard icon or say "Text mode" / "Type karo." Type your question instead of speaking. NidaBot will respond with text and (optionally) voice.
  • Try different phrasing. NidaBot is trained on multiple Urdu and English dialects. If your first phrasing is not understood, try saying the same thing in different words. For example, instead of "Mera result batao," try "Mere number kya hain?" or "Merit kitni hai?"
  • Speak slowly and clearly. In noisy environments, NidaBot may have difficulty separating your voice from background noise. Move to a quieter area or use text mode.
  • Provide feedback. When NidaBot misunderstands, click the "That was not what I asked" button (thumbs down icon). This feedback helps NidaBot learn and improve for your accent and phrasing style.

Problem: "I cannot log in"

Solutions:

  • Incorrect password. Most login failures are due to mistyped passwords. Click the eye icon in the password field to see what you typed. Check Caps Lock. Use "Forgot Password" to reset if you cannot remember your password.
  • Account locked. After 5 failed attempts, your account locks for 15 minutes. Wait 15 minutes and try again, or contact the IT helpdesk to unlock immediately.
  • Account disabled or not yet created. If you recently joined the university, your account may not be set up yet. Contact your department or the IT helpdesk.
  • Wrong URL. Make sure you are visiting the correct AegisCore address for your university https://aegiscore.youruniversity.edu. Bookmark the correct URL to avoid this issue.
  • Browser issue. Try clearing your browser cache and cookies, or try a different browser. Outdated cached files can sometimes prevent the login page from loading correctly.

Running Finance Reports

Fee Collection Best Practices

Effective fee collection is about systems, communication, and empathy. Here are best practices refined from AegisCore deployments at universities across Pakistan and internationally:

Communication Cadence

Students are more likely to pay on time when they receive consistent, clear, and non-threatening communication. AegisCore automates this cadence:

  • 30 days before due date: "Friendly reminder" notification and email. Lists upcoming fee deadlines and amounts. Includes a direct link to the payment page.
  • 14 days before due date: "Deadline approaching" notification. Includes a "Pay Now" button that opens directly to the RAAST payment page with the amount pre-filled.
  • 7 days before due date: "One week remaining" notification. Mentions the specific consequences of late payment per university policy (late fee amount, registration hold, etc.).
  • Day of deadline: "Today is the deadline" notification sent at 9:00 AM. Includes a reminder that payments received after 5:00 PM may be considered late.
  • 1 day after deadline: "Payment overdue" notification. Friendly tone: "It looks like we missed the deadline. Is everything okay? Please contact the finance office if you are experiencing difficulties."
  • 7 days after deadline: "Second reminder" notification. Slightly more urgent tone, but still supportive: "Your payment is now one week overdue. We want to help. Please contact us to discuss payment options."

These automated messages should always include contact information for the finance office and a note that the student can request a confidential meeting to discuss payment difficulties.

Payment Plan Philosophy

Payment plans are the most effective tool for reducing defaults while maintaining student enrollment. A student who pays in installments is infinitely better than a student who drops out because they cannot afford a lump-sum payment. AegisCore's payment plan system is designed to make installment arrangements easy for both students and finance staff. Key principles:

  • Automatic approval for small amounts: For amounts under 50,000 PKR, payment plans should be automatically approved without requiring management review. This reduces administrative overhead and gets students onto payment plans quickly.
  • Reasonable installment sizes: Monthly installments should not exceed 25% of the typical monthly income for students at your institution. An installment that a student cannot afford is worse than no plan at all.
  • Grace period for missed installments: A student who misses one installment by a few days should not be penalized. Give a 7-day grace period before flagging the plan as "missed."
  • Plan renegotiation: If a student's circumstances change mid-plan, they should be able to request plan adjustments. Life is unpredictable. AegisCore allows finance staff to modify active payment plans with appropriate documentation.

Understanding DefaultSense Risk Factors

DefaultSense does not simply look at whether a student has paid or not. It analyzes multiple risk factors to determine the alert color. Understanding these factors helps finance staff make informed decisions about how to approach each student:

  • Payment History: Has the student consistently paid on time in previous semesters, or do they have a history of late payments? A student who has always paid on time but missed one deadline is less risky than a student who is habitually late.
  • Amount Outstanding: A student who owes 5,000 PKR for a single lab fee is in a different situation than a student who owes 150,000 PKR across tuition, hostel, and transport. DefaultSense weights the amount relative to the student's total annual fees.
  • Days Overdue: The longer a payment is overdue, the higher the risk. DefaultSense tracks not just whether a payment is late, but how many days have passed since the deadline.
  • Communication Responsiveness: Has the student responded to previous fee reminders? Students who engage with the finance office (reply to emails, attend meetings, request payment plans) are flagged as lower risk than those who ignore all communication.
  • Academic Standing: Students on academic probation or with very low attendance are at higher risk of dropping out, which makes fee default more likely. DefaultSense cross-references academic data (with appropriate privacy safeguards) to identify students who may need holistic support.
  • External Factors (Optional): If your university tracks scholarship status, financial aid applications, or family income brackets, DefaultSense can incorporate these factors to provide a more complete picture. These external factors are optional and must be configured by an administrator.

DefaultSense is a decision-support tool, not an automated decision-maker. The color code suggests a level of urgency, but finance staff should always use their judgment. A student marked ORANGE because of a large amount overdue might actually be waiting for a confirmed scholarship disbursement. A student marked GREEN might have personal circumstances that put them at risk. Always have a conversation before taking action.

Disciplinary Cases

1Open a disciplinary case

Go to "Admin" → "Discipline" → "New Case." Enter: student name/ID, incident date, incident description (detailed, factual account of what happened), severity level, and any immediate actions taken. Attach any evidence files (reports, witness statements, photos). Click "Create Case." The case is assigned a unique case number and the student is notified (privately, within AegisCore).

Severity Levels

  • Level 1 — Minor: Classroom disruption, minor dress code violation, first-time minor policy breach. Resolution: verbal warning, documented in system. No formal hearing needed.
  • Level 2 — Moderate: Repeated minor offenses, academic dishonesty (first offense), verbal altercation, unauthorized absence. Resolution: written warning, meeting with department head, possible community service or academic penalty.
  • Level 3 — Serious: Physical altercation, vandalism, serious academic fraud, harassment, theft. Resolution: formal disciplinary committee hearing, possible suspension (1–2 semesters), mandatory counseling.
  • Level 4 — Severe: Violence, sexual misconduct, criminal activity, repeated serious offenses. Resolution: full disciplinary tribunal, possible expulsion. Legal authorities may be involved if the conduct is criminal.
🚨
Important Due Process Before Any Sanction: Every student has the right to: (1) Know the charges against them — in writing, clearly stated. (2) Have time to prepare a response — minimum 5 working days for Level 3+, minimum 3 days for Level 2, minimum 1 day for Level 1. (3) Present their side of the story to an impartial committee or administrator. (4) Bring a support person (faculty advisor, fellow student) to any hearing. (5) Appeal a decision to a higher authority. No sanction may be imposed before due process is complete. AegisCore tracks every step of the process to ensure compliance with these rights.
2Close a case

After the resolution is reached (warning issued, hearing completed, appeal decided), go to the case and click "Close Case." Enter: final resolution, sanctions (if any), date of resolution, and any follow-up actions (counseling, probation period, etc.). The student receives notification of the outcome. Closed cases are archived but remain accessible to authorized administrators for reference in future cases.

Go to "My Settings" → "Accessibility" → "High Contrast." Toggle to enable. High contrast mode increases the contrast between text and backgrounds beyond the default dark mode. Borders become more visible, links are underlined, and the color palette adjusts to ensure a minimum contrast ratio of 7:1. This helps users with low vision or color blindness.

Slow Speech on NidaBot ("Dhire Bolein")

If NidaBot speaks too quickly, you can slow it down. When NidaBot is open, say "Dhire bolein" or click the speed control (1x button) in the NidaBot panel. Choose 0.75x or 0.5x speed. AegisCore includes several features specifically designed for users with color vision deficiency (color blindness) or other visual processing differences:

Color Blindness Modes

Go to "My Settings" → "Accessibility" → "Color Profile." Font and Typography Options

Beyond text size, AegisCore offers typography customization for users with dyslexia or visual processing differences:

  • Dyslexia-Friendly Font: Enable "OpenDyslexic" font from Accessibility settings. This font uses heavier bottom weighting on characters to reduce letter swapping and flipping, which can improve reading speed and comprehension for users with dyslexia.
  • Line Spacing: Adjust from Default (1.5) to Wide (2.0) or Extra Wide (2.5). Increased line spacing reduces visual crowding and improves readability for many users, particularly when reading long blocks of text like course descriptions or report narratives.
  • Letter Spacing: Adjust character spacing from Default to Wide or Extra Wide. Increased letter spacing can help users who experience visual crowding between adjacent letters.
  • Paragraph Spacing: Add extra space between paragraphs to create clearer visual separation between sections of text.

Reduced Motion and Animation Settings

For users who experience discomfort or disorientation from motion effects:

  • Reduce Motion: Disables all CSS animations, transitions, and parallax effects. Page transitions become instant. Sidebar slide animations are replaced with immediate show/hide. Loading spinners are replaced with static progress indicators.
  • Disable Auto-Play: Prevents videos and audio from playing automatically. All media requires an explicit play action from the user.
  • Disable Parallax: Removes parallax scrolling effects from hero strips and background elements.

These settings are available from "My Settings" → "Accessibility" → "Motion & Animation." AegisCore also respects the prefers-reduced-motion operating system setting — if you have enabled "Reduce motion" in your device's system settings, AegisCore automatically disables animations without requiring you to change settings within the application.

Appendix A — Preventive Maintenance & Monitoring

Regular maintenance procedures and monitoring setup to keep your AegisCore deployment healthy and performant.

Preventive Maintenance Schedule

Regular maintenance prevents most problems before they occur. Follow this schedule to keep your AegisCore instance healthy:

Daily Checks (5 minutes)

  • Verify the health check endpoint returns "status": "healthy" (curl -s http://localhost:3000/api/health)
  • Check that all containers are running (docker ps --format "table {{.Names}}\t{{.Status}}")
  • Review the last 50 lines of web server logs for errors (docker logs aegiscore-web --tail 50 | grep -i error)
  • Verify that the most recent automated backup completed successfully (check Admin → Backups)
  • Check disk usage (df -h /) — alert if usage exceeds 80%

Weekly Checks (15 minutes)

  • Review the full backup logs for any warnings (docker logs aegiscore-backup --since 7d | grep -i warn)
  • Check Redis memory usage (docker stats aegiscore-redis --no-stream)
  • Review failed login attempts in the application logs (Admin → Security → Login Attempts)
  • Check for any pending database migrations (./scripts/migrate.sh status)
  • Verify SSL certificate expiry date (sudo certbot certificates) — should be more than 30 days away
  • Update system packages (sudo apt update && sudo apt upgrade -y) — only apply non-Docker system updates; Docker images are updated separately

Monthly Checks (30 minutes)

  • Review all user accounts for inactive users (Admin → Users → filter by "Last Login > 90 days"). Disable accounts for users who have left the institution.
  • Run a manual full backup and verify it restores correctly in a sandbox environment
  • Check license expiry date (Admin → Licenses) — renew if less than 30 days remain
  • Review application error rates (Support → Error Dashboard) — investigate persistent errors
  • Clean up old Docker images (docker system prune -a --filter "until=720h")
  • Rotate database credentials if required by your security policy
  • Review the AegisCore release notes for any security patches (Support → Release Notes)

Quarterly Checks (1 hour)

  • Perform a full disaster recovery drill: restore from backup, verify all data is intact, time the entire process
  • Review and update firewall rules — remove any rules that are no longer needed
  • Audit user permissions — ensure that no user has more access than their role requires
  • Review audit logs for any suspicious activity (Admin → Security → Audit Log)
  • Update Docker images to the latest versions (docker compose pull && docker compose up -d)
  • Test notification delivery (email and in-app) to ensure users are receiving important alerts

Log Management

Docker containers generate logs continuously. Without log rotation, logs can fill your disk. Configure Docker log rotation to prevent this:

# Edit Docker daemon configuration sudo nano /etc/docker/daemon.json

Add or modify the configuration:

{ "log-driver": "json-file", "log-opts": { "max-size": "10m", "max-file": "3" } }

This limits each container's log to 10 MB per file, keeping a maximum of 3 files (30 MB total per container). Restart Docker after making changes: sudo systemctl restart docker. Existing containers must be recreated to pick up the new log settings: docker compose up -d --force-recreate.

For production deployments, consider forwarding logs to a centralized log management service such as ELK Stack (Elasticsearch, Logstash, Kibana), Grafana Loki, or a cloud provider's log service (AWS CloudWatch, Azure Monitor, Google Cloud Logging). Centralized logs allow you to search across all containers and services from a single interface and retain logs for compliance purposes (typically 90 days for most regulatory requirements).

Appendix C — Glossary of Terms

Definitions of technical terms, acronyms, and AegisCore-specific vocabulary used throughout this manual and the application.

Technical Infrastructure Terms

Container (Docker)
A lightweight, standalone, executable package that includes everything needed to run a piece of software: code, runtime, system tools, libraries, and settings. AegisCore runs as multiple Docker containers (web server, database, Redis, worker), each isolated from the others but able to communicate over a private network.
Docker Compose
A tool for defining and running multi-container Docker applications. AegisCore uses a docker-compose.yml file that describes all the containers, their configurations, and how they connect to each other. A single docker compose up command starts the entire stack.
Docker Image
A read-only template with instructions for creating a Docker container. Think of it as a snapshot of a pre-configured environment. AegisCore Docker images are downloaded (pulled) from a container registry and then instantiated as running containers.
Environment Variable
A dynamic-named value that can affect the way running processes behave on a computer. AegisCore uses environment variables (stored in the .env file) for configuration: database URLs, secret keys, feature flags, and deployment settings. Environment variables are never committed to version control.
Health Check
An endpoint (/api/health) that returns the current status of all AegisCore services. Monitoring systems ping this endpoint to determine if the application is functioning correctly. A response of {"status": "healthy"} means all services are operational.
HTTPS / SSL / TLS
Technologies that encrypt communication between a user's browser and the AegisCore server. HTTPS (the padlock icon in your browser) ensures that passwords, grades, and financial data cannot be intercepted or read by third parties. AegisCore uses Let's Encrypt for free, automated SSL certificates.
JWT (JSON Web Token)
A compact, URL-safe means of representing claims to be transferred between two parties. AegisCore uses JWTs for user authentication: when you log in, the server issues a JWT that your browser sends with each subsequent request to prove your identity. JWTs are cryptographically signed to prevent forgery.
Load Balancer
A device or service that distributes network traffic across multiple servers. In large AegisCore deployments, a load balancer sits in front of multiple web server containers, directing each user request to the least busy server. This provides both improved performance and high availability (if one server fails, the others continue serving).
Migration (Database)
A script that modifies the database structure (schema) in a controlled, versioned way. When AegisCore is updated, migration scripts add new tables, modify existing columns, or create new indexes. Migrations are applied automatically during deployment and can be rolled back if needed.
PostgreSQL
A powerful, open-source relational database system. AegisCore stores all data (students, courses, grades, fees, attendance, settings) in PostgreSQL. It was chosen for its reliability, ACID compliance, advanced security features (row-level security), and robust backup/replication capabilities.
Redis
An in-memory data structure store used as a cache and message broker. AegisCore uses Redis to: (a) cache frequently accessed data for faster page loads, (b) store user session information, (c) queue background jobs (emails, reports, analytics) for the worker to process, and (d) manage rate limiting.
Reverse Proxy (Nginx)
A server that sits between the internet and the AegisCore application, handling incoming requests and forwarding them to the appropriate service. Nginx handles SSL termination (encryption/decryption), serves static files, compresses responses for faster delivery, and provides an additional layer of security by hiding the application server from direct internet access.
SMTP
Simple Mail Transfer Protocol — the standard protocol for sending email. AegisCore connects to an SMTP server to send: password reset emails, welcome emails, fee payment confirmations, attendance warnings, grade appeal notifications, and scheduled reports. You configure your SMTP server during the bootstrap process.
SSH (Secure Shell)
A cryptographic network protocol for operating network services securely over an unsecured network. IT administrators use SSH to connect to the AegisCore server remotely, run deployment scripts, check logs, and perform maintenance. SSH connections are encrypted end-to-end.
WAL (Write-Ahead Log)
A PostgreSQL feature that records all changes to the database before they are applied. WAL files are continuously archived to a backup location, enabling point-in-time recovery: in a disaster, you can restore the database to its exact state at any moment, down to the second, by replaying WAL files from the last full backup.

AegisCore-Specific Terms

DefaultSense
AegisCore's AI-powered fee defaulter prediction system. DefaultSense analyzes payment history, amounts outstanding, days overdue, communication responsiveness, and academic standing to assign a color-coded risk level (Green, Yellow, Orange, Red) to each student. The system is designed as a decision-support tool — it helps finance staff prioritize outreach, but human judgment always makes the final decision. DefaultSense includes built-in ethical guardrails to protect student dignity and privacy.
MORA Compliance
The Ministry of Religious Affairs (MORA) in Pakistan requires universities to track and report on the status of international students, including visa validity, enrollment status, and academic progress. AegisCore's MORA Compliance module automates this tracking with color-coded deadline warnings (90, 60, 30, 14, and 7 days before visa expiry) and generates the required reports and enrollment letters for submission.
NidaBot
AegisCore's AI-powered voice assistant, named after "Nida" (Urdu for "voice" or "call"). NidaBot accepts spoken questions in both English and Urdu and responds conversationally with information from the student's academic record, fee status, schedule, and more. NidaBot can perform multi-step tasks (like walking a student through the fee payment process) and gets better at understanding users over time through machine learning.
RAAST
Pakistan's instant digital payment system, operated by the State Bank of Pakistan. RAAST enables real-time, low-cost digital payments between individuals, businesses, and government entities. AegisCore integrates with RAAST so students can pay their university fees instantly through any bank's mobile app or internet banking, with payments reflecting in AegisCore within seconds.
SafeSpace
AegisCore's built-in mental health support feature. SafeSpace provides three pathways: self-help resources (articles, videos, guided exercises), peer support (trained student listeners), and professional counseling (licensed therapists). All SafeSpace interactions are confidential and anonymous — no one except the assigned counselor knows a student has used the service. SafeSpace is designed to reduce the stigma around seeking mental health support.
Super Admin
The highest-level administrator account in an AegisCore installation. Created during the bootstrap process, the super admin has access to all tenants (universities), system-level settings, license management, and global configuration. The super admin account should be used only for system administration — day-to-day university operations should be performed by tenant-level administrators.
Tenant
A single institution, campus, or organizational unit within an AegisCore installation. Each tenant has its own isolated database schema with completely separate students, faculty, courses, fees, and reports. A student at one tenant cannot see any data from another tenant. Multi-tenancy allows a single AegisCore server to serve multiple independent universities while maintaining strict data isolation.
Tenant Administrator
An administrator account with full control over a single tenant (university) but no access to other tenants or system-level settings. Tenant administrators manage students, faculty, courses, fees, and all day-to-day operations within their university. They cannot access the AegisCore license, global secrets, or server configuration.

Appendix F — Migration Guide: Switching Cloud Providers

Step-by-step process for moving your AegisCore deployment from one cloud provider to another without data loss.

Overview

You may need to migrate your AegisCore deployment between cloud providers for various reasons: cost optimization, changing institutional partnerships, regulatory requirements, or performance improvements. This guide covers a safe, tested migration process that minimizes downtime and preserves all data.

🚨
Important Practice this migration on a staging environment before performing it on production. Every AegisCore installation is slightly different, and you need to verify that your specific configuration migrates correctly. Plan for 2-4 hours of total migration time, including verification. Schedule the migration during a low-usage period (weekend, holiday, or late night). Notify all users at least 48 hours in advance through AegisCore's announcement system.

Pre-Migration Checklist

  1. Take a full verified backup: Run ./scripts/backup.sh --full --tag="Pre-migration to [new provider]" --retain 365. Verify the backup with ./scripts/restore.sh --list and confirm the backup shows "verified" status.
  2. Export your configuration: Copy your .env file (without secrets) to document all settings. Run grep -v "^#" .env | grep -v "^$" | cut -d= -f1 to list all environment variables without their values.
  3. Record your Installation ID: Go to Admin → Licenses and note your Installation ID. You will need this to request a new license key for the new server.
  4. Provision the new infrastructure: Set up your database and server on the new cloud provider following Section A3 (Production Deployment). Do not run the deployment yet.
  5. Request a new license key: Contact your AegisCore representative with your current Installation ID and inform them of the migration. Request a new license key for the new Installation ID.
  6. Test connectivity: From your new server, verify you can reach the new database and any external services (SMTP, monitoring, backups).

Migration Steps

1Put the old system in maintenance mode

On your existing deployment, enable maintenance mode to prevent users from making changes during migration:

./scripts/maintenance.sh on

Users will see: "AegisCore is temporarily unavailable for scheduled maintenance. We will be back shortly." This prevents new data from being created during the migration, ensuring no data is lost.

2Take the final backup from the old system

Take one final backup that captures all data up to the moment maintenance mode was enabled:

./scripts/backup.sh --full --tag="Final backup before migration"

Note the exact timestamp of this backup. Any data changes after this timestamp will not be in the new system (but since maintenance mode is on, no changes should occur).

3Transfer the backup to the new server

Copy the backup files from the old server to the new server. If both servers are cloud-based, the fastest method is using the cloud provider's object storage as an intermediary:

# On old server: upload backup to S3/Azure Blob/GCS ./scripts/backup.sh --upload-s3 # On new server: download backup from S3/Azure Blob/GCS ./scripts/backup.sh --download-s3 --tag="Pre-migration to [new provider]"

If using Supabase, contact Supabase support for a database dump export. If using a VPS, use SCP to transfer the backup directory: scp -r /var/backups/aegiscore/* user@new-server:/var/backups/aegiscore/

4Set up the new environment

On the new server, run the bootstrap script with the new database connection string and other settings matching your old configuration:

./scripts/bootstrap-env.sh

Use the same admin email, SMTP settings, and deployment mode. Only the database connection string and domain should be new (if changing domains).

5Restore the backup on the new server

Restore the database from the backup you transferred:

./scripts/restore.sh --latest

The database migrations will run automatically after the restore. Verify the restore was successful by checking the health endpoint.

6Upload the new license key

Log in to the new deployment as super admin and upload the new license key file in Admin → Licenses. Verify that all features are enabled and the license shows as Active.

7Update DNS and verify

Update your domain's DNS A record to point to the new server's IP address. DNS changes typically propagate within 5-30 minutes (though some DNS providers take up to 48 hours). While waiting for propagation:

  • Access the new server directly via its IP address to verify everything works.
  • Test logging in with various user roles.
  • Verify that emails are being sent correctly.
  • Check that all data (students, courses, grades, fees) is present and correct.
  • Run the health check: curl -s http://localhost:3000/api/health

Once DNS propagates, access AegisCore via your domain and perform the same verifications.

8Decommission the old server

After confirming the new deployment is fully operational for at least 48 hours without any issues, shut down the old server:

# On old server ./scripts/demo-down.sh --clean # For demo # OR ./scripts/deploy.sh down --clean # For production

Do NOT delete the old server or its backups for at least 30 days after migration. If any issues are discovered with the new deployment, you may need to access the old data as a reference or fallback.

Post-Migration Verification Checklist

  1. Verify all users can log in with their existing credentials.
  2. Verify student grades, attendance records, and fee histories are complete.
  3. Verify faculty can access their courses and take attendance.
  4. Verify finance staff can process payments and generate reports.
  5. Verify automated emails (notifications, password resets) are being delivered.
  6. Verify automated backups are running on the new server.
  7. Verify SSL certificates are valid on the new domain/IP.
  8. Verify monitoring and alerting are configured for the new server.
  9. Send a test announcement to all users confirming the migration is complete.
  10. Archive the old server's final backup in a secure, long-term storage location.

Appendix D — Performance Tuning Guide

Specific settings and configurations to optimize AegisCore performance for your institution's size and usage patterns.

Database Performance

The PostgreSQL database is the most common performance bottleneck. These tuning steps can significantly improve response times, especially for institutions with more than 1,000 active students:

Connection Pooling

By default, AegisCore opens a direct database connection for each request. Under heavy load, this can exhaust PostgreSQL's connection limit (typically 100 by default). Enable PgBouncer connection pooling in your .env file:

DATABASE_POOL_ENABLED=true DATABASE_POOL_SIZE=20 DATABASE_POOL_OVERFLOW=10

This limits direct database connections to 20 (with 10 overflow), while allowing hundreds of concurrent users to share those connections efficiently. If you are using Supabase, the connection pooler is already enabled on port 6543.

Query Caching

AegisCore caches frequently accessed data in Redis to reduce database load:

CACHE_ENABLED=true CACHE_TTL=300 # Cache entries expire after 5 minutes CACHE_STUDENT_LIST=true # Cache student roster queries CACHE_COURSE_LIST=true # Cache course catalog queries CACHE_PERMISSIONS=true # Cache user permission checks

Increase CACHE_TTL to 600 (10 minutes) or 1800 (30 minutes) for data that changes infrequently. Do not cache data that must be real-time, like attendance records or fee payment status.

Database Indexes

AegisCore automatically creates indexes for commonly queried columns during migration. However, if your institution has specific reporting needs (e.g., frequent queries by a non-standard field), you can add custom indexes. Contact AegisCore support before adding custom indexes — incorrectly designed indexes can decrease performance. The support team can analyze your query patterns and recommend optimal indexes.

Web Server Performance

Worker Processes

Adjust the number of application worker processes based on your server's CPU cores:

WEB_WORKERS=4 # Set to (2 * CPU cores) + 1 WEB_THREADS_PER_WORKER=2 # Threads per worker process

For a server with 4 vCPUs, set WEB_WORKERS=9. Monitor CPU usage during peak hours and adjust downward if CPU consistently exceeds 90%.

Static Asset Caching

Configure Nginx to cache static files (CSS, JavaScript, images) in the browser:

STATIC_CACHE_MAX_AGE=31536000 # Cache static assets for 1 year ENABLE_GZIP=true # Compress responses

Static assets include version hashes in their filenames, so they can be cached aggressively without risk of serving outdated files after an update.

Background Worker Performance

Worker Concurrency

Control how many background jobs the worker processes simultaneously:

WORKER_CONCURRENCY=5 # Number of simultaneous jobs WORKER_QUEUES=default,mail,reports,analytics # Dedicated queues

For institutions that send many emails (large student body, frequent notifications), increase WORKER_CONCURRENCY to 10. For institutions that generate many reports, dedicate a queue: set up a second worker container with WORKER_QUEUES=reports,analytics and higher concurrency.

Memory Tuning

ComponentRecommended LimitSetting
PostgreSQL25% of total RAMPOSTGRES_SHARED_BUFFERS=2GB (on 8GB server)
Redis10-15% of total RAMREDIS_MAXMEMORY=1gb (on 8GB server)
Web Server500MB per workerWEB_WORKER_MEMORY=500m

Appendix G — Security Best Practices Checklist

Essential security measures every AegisCore administrator should implement to protect student data and institutional information.

Access Control

  • Principle of Least Privilege: Every user account should have only the permissions necessary for their role. A faculty member does not need access to financial reports. A finance clerk does not need access to student grades. Review user permissions quarterly.
  • Strong Password Policy: Enforce minimum 12-character passwords with complexity requirements (uppercase, lowercase, digit, special character). Passwords should expire every 90 days. Prevent reuse of the last 5 passwords. These policies are configured in Admin → Security → Password Policy.
  • Multi-Factor Authentication (MFA): Enable MFA for all administrative accounts (super admins, tenant admins, finance managers). AegisCore supports TOTP-based MFA (Google Authenticator, Authy, Microsoft Authenticator). Enable in Admin → Security → MFA Settings.
  • Session Management: Set session timeout to 15 minutes for administrative accounts and 2 hours for student and faculty accounts. Force re-authentication for sensitive operations (changing roles, viewing full financial reports, exporting student data).
  • IP Allowlisting: For highly sensitive deployments, restrict administrative access to specific IP addresses or VPN ranges. Configure in Admin → Security → IP Restrictions.

Data Protection

  • Encryption at Rest: Ensure database encryption is enabled (it is by default). The database encryption key is generated during bootstrap. Store it securely and rotate it every 180 days.
  • Encryption in Transit: All communication between users and AegisCore must use HTTPS (TLS 1.3). Let's Encrypt certificates auto-renew, but verify renewal is working monthly. Internal communication between AegisCore services (web to database, web to Redis) should use TLS if the services are on different servers.
  • Backup Encryption: Backup files should be encrypted before being stored. Enable backup encryption in the .env file: BACKUP_ENCRYPTION_ENABLED=true. The backup encryption key is separate from the database encryption key.
  • Data Minimization: Only collect data that is necessary. Do not store sensitive information (full credit card numbers, national ID numbers, medical details) unless absolutely required. If you must store it, encrypt it with field-level encryption.
  • Data Retention Policy: Define how long different types of data are retained. Student academic records should be kept permanently (or per regulatory requirements). System logs should be kept for 90 days. User session data should be kept for 24 hours. Configure in Admin → Security → Data Retention.

Network Security

  • Firewall Configuration: The only ports that should accept inbound connections are 443 (HTTPS) and 80 (HTTP, redirect to 443). Port 22 (SSH) should be restricted to known administrator IP addresses. All other ports should be closed.
  • DDoS Protection: If using a cloud provider, enable their DDoS protection service (AWS Shield, Azure DDoS Protection, Google Cloud Armor). AegisCore includes built-in rate limiting (20 requests per 60 seconds per IP for login, 100 requests per 60 seconds for general API access).
  • VPN for Administrative Access: Require administrators to connect through a VPN before accessing the AegisCore server via SSH. This adds a layer of authentication and encryption beyond SSH keys.
  • Regular Security Scans: Run a vulnerability scanner (such as OWASP ZAP or Nikto) against your AegisCore deployment quarterly. Review and address any findings. Contact AegisCore support if you need help interpreting scan results.

Monitoring and Incident Response

  • Audit Logging: Enable comprehensive audit logging (it is on by default). All administrative actions, login attempts (successful and failed), data exports, and configuration changes are logged with timestamps, user IDs, and IP addresses. Audit logs are immutable and cannot be deleted.
  • Alert Configuration: Set up alerts for: (a) 5 or more failed login attempts from the same IP within 5 minutes (potential brute force attack), (b) any login from a new, unrecognized device or location, (c) any change to user permissions or roles, (d) any bulk data export (more than 100 records), and (e) any change to security settings.
  • Incident Response Plan: Document a clear incident response procedure: (1) Identify and contain — disconnect the affected server or service. (2) Assess impact — which data was potentially accessed? (3) Notify — inform university leadership and, if required by law, affected individuals. (4) Remediate — fix the vulnerability that was exploited. (5) Recover — restore from clean backup after the vulnerability is patched. (6) Review — document lessons learned and update security measures.
  • Security Contacts: Maintain an up-to-date list of security contacts: AegisCore support, university IT security team, university legal counsel, and university communications/PR (for public statements if needed). Store this list outside of AegisCore in case the system itself is compromised.

Software Maintenance

  • Regular Updates: Apply AegisCore updates within 7 days of release for security patches, within 30 days for feature updates. Subscribe to the AegisCore security mailing list (security@aegiscore.local) for notifications of critical vulnerabilities.
  • Dependency Updates: Docker images include all dependencies (PostgreSQL, Redis, Nginx). When AegisCore releases a new Docker image, it includes the latest secure versions of all dependencies. You do not need to update dependencies separately.
  • Operating System Updates: Keep the host operating system (Ubuntu) updated with security patches. Run sudo apt update && sudo apt upgrade -y weekly. Configure unattended-upgrades for security patches: sudo apt install unattended-upgrades && sudo dpkg-reconfigure unattended-upgrades.

Compliance Considerations

Depending on your institution's location and the data you store, you may need to comply with specific regulations:

  • FERPA (United States): AegisCore includes FERPA-compliant access controls, audit logging, and data export capabilities. Student educational records are protected by role-based access and can be provided to authorized parties upon request.
  • GDPR (European Union): If you have students from the EU, AegisCore supports GDPR requirements: data portability (export all data for a user as JSON/CSV), right to erasure (delete all data for a user), and consent management (record when and how users consented to data processing).
  • HEC Pakistan Data Protection Guidelines: AegisCore complies with Higher Education Commission of Pakistan guidelines for student data handling, including data localization (data stored within Pakistan if required), access controls, and annual security audits.
  • PCI DSS (Payment Card Industry): AegisCore does not store credit card numbers. All payments go through RAAST or your payment gateway, which handles PCI compliance. AegisCore only stores transaction references and amounts.

Appendix H — Staff Training & Onboarding Guide

A structured plan for training new staff, faculty, and student users on AegisCore, with role-specific training modules and assessment checklists.

Training Philosophy

Successful AegisCore adoption depends on effective training. Users who understand the system are more productive, make fewer errors, and require less support. The following training plan is based on the principle of "learn by doing" — each module includes hands-on exercises that users complete in a sandbox or training environment before using the production system with real data.

Training Environment Setup

Before training begins, set up a dedicated training tenant (see Section A5, "Adding a Second University"). Name it "[Your University] Training." Populate it with realistic but clearly fake data — sample students with obviously made-up names, sample courses from fictional departments, and sample fee records. This training environment is a safe place for users to experiment, make mistakes, and learn without any risk to real student data.

Module 1: Universal Basics (All Roles, 30 minutes)

Every user, regardless of role, should complete this module first:

Appendix I — Data Privacy & Student Rights

Understanding student data privacy rights, institutional obligations, and how AegisCore helps you maintain compliance.

Student Data Rights

Students have fundamental rights regarding their personal data stored in AegisCore. These rights are based on international privacy principles and may be supplemented by specific national laws. As the data controller, your institution is responsible for upholding these rights. AegisCore provides the technical tools to do so.

Right to Access

Students have the right to know what personal data you hold about them and how it is used. AegisCore supports this through:

  • Self-service access: Students can view their own academic records, financial data, attendance history, and personal information through their dashboard at any time. No staff intervention is needed.
  • Data export: Students can export their complete AegisCore data as a machine-readable JSON file from My Profile → Privacy → "Export My Data." The export includes: personal information, academic history, fee records, attendance logs, documents, and notifications.
  • Subject Access Requests (SARs): For formal legal requests, administrators can generate a comprehensive data report from Admin → Privacy → Subject Access Request. This produces a PDF containing all data held about the individual, including system-generated data (login timestamps, IP addresses, audit logs) that is not normally visible to users.

Right to Rectification

Students have the right to have inaccurate personal data corrected. AegisCore supports this through:

  • Self-service corrections: Students can update their contact information (email, phone number, address) from My Profile. These changes are logged in the audit trail.
  • Grade appeals: The grade appeal process (Section B3) is a formal mechanism for correcting potentially inaccurate academic records.
  • Administrative corrections: Registrars and administrators can correct data on a student's behalf. All corrections are logged with the administrator's identity, timestamp, and reason, creating an immutable audit trail.

Right to Erasure (Right to be Forgotten)

Under certain circumstances, students may request that their personal data be deleted. AegisCore supports qualified erasure through the Admin → Privacy → Data Erasure interface. Important considerations:

  • Academic records may be exempt: Most jurisdictions recognize that educational institutions have a legitimate need to retain academic records (transcripts, degrees conferred) even after a student leaves. These records may be retained even if other personal data is deleted.
  • Financial records may be required: Tax and audit requirements typically mandate retention of financial records for 5-7 years. Fee payment records cannot be deleted before the statutory retention period expires.
  • Selective erasure: AegisCore supports erasing specific categories of data (contact information, profile data, communications) while preserving academic and financial records required for compliance.
  • Irreversible action: Data erasure is permanent and irreversible. AegisCore requires dual authorization (two administrators must confirm) before executing a data erasure request.

Right to Data Portability

Students have the right to receive their personal data in a structured, commonly used, machine-readable format and to transmit that data to another institution. AegisCore supports this through the standard data export (JSON format) and additional CSV exports for specific data categories. For bulk portability (entire graduating class), contact AegisCore support for a custom export script.

Institutional Obligations

Data Processing Records

Maintain a record of all data processing activities. AegisCore helps by providing an automated data processing audit report (Admin → Privacy → Processing Activities) that documents: what data is collected, why it is collected, how it is stored, who has access, how long it is retained, and when it is deleted. Review and update this record annually.

Data Breach Notification

If a data breach occurs (unauthorized access to student data), your institution may be legally required to notify affected individuals and regulatory authorities within a specific timeframe (typically 72 hours under GDPR, varies by jurisdiction). AegisCore's audit logs and access records provide the information needed to: (1) determine exactly which records were accessed, (2) identify which individuals were affected, (3) document the timeline of the breach, and (4) generate notification letters. Run Admin → Privacy → Breach Impact Assessment to quickly generate a report covering all these elements.

Privacy Impact Assessment

Before implementing new data processing activities (e.g., enabling a new AegisCore module that collects additional student data), conduct a Privacy Impact Assessment. Document: the purpose of the new data collection, the categories of data involved, the legal basis for processing, the security measures protecting the data, and the retention period. AegisCore provides a PIA template at Admin → Privacy → Privacy Impact Assessment.

Privacy by Design in AegisCore

AegisCore was built with privacy principles embedded in its architecture:

  • Data Minimization: AegisCore only collects data that is necessary for university operations. Optional fields are clearly marked, and users are informed why additional data is requested.
  • Purpose Limitation: Data collected for one purpose (e.g., attendance tracking) is not automatically available for another purpose (e.g., DefaultSense analysis). Cross-module data access requires explicit configuration and is logged.
  • Storage Limitation: Automated data retention policies delete or anonymize data when it is no longer needed. Configure retention periods in Admin → Privacy → Retention Policies.
  • Access Limitation: Role-based access control ensures that users can only see data relevant to their job function. All access is logged for audit purposes.
  • Transparency: The data processing audit report and privacy policy (configurable in Admin → Branding → Privacy Policy) inform users about what data is collected and how it is used.

To see which version of AegisCore you are running:

  • Via the admin dashboard: Go to Admin → System Info. The version number and build date are displayed at the top of the page.
  • Via the login page: The version number is printed in small text at the bottom of the login page.

Upgrading AegisCore

⚠️
Watch out Always take a full verified backup before upgrading. Upgrades are generally safe and reversible, but a backup ensures you can recover if something unexpected happens. Test the upgrade on your staging/sandbox environment before upgrading production.
1Read the release notes

Before upgrading, read the release notes for all versions between your current version and the target version. Pay special attention to: breaking changes (features that have been removed or changed in incompatible ways), database migrations that modify the schema, new required environment variables, deprecated features scheduled for removal, and any special upgrade instructions. Release notes are available at Support → Release Notes.

2Back up your current deployment

Take a full manual backup with a descriptive tag:

./scripts/backup.sh --full --tag="Before upgrade from v2.3 to v2.4" --retain 90

Verify the backup: ./scripts/restore.sh --list and confirm the backup appears with "verified" status.

3Pull the new Docker images

Download the latest Docker images for the new version:

docker compose pull

This downloads the new images but does not restart any services. Your current deployment continues running.

4Apply the upgrade

Restart all services with the new images and run any pending database migrations:

docker compose up -d ./scripts/migrate.sh up

AegisCore will be briefly unavailable (typically 10-30 seconds) as containers restart. Database migrations run while the system is coming back online.

5Verify the upgrade

Check the health endpoint to confirm the new version is running:

curl -s http://localhost:3000/api/health

Verify the version number matches the expected new version. Log in and test core functionality: can students view grades? Can faculty take attendance? Can finance generate a report? Are emails being sent?

Rolling Back an Upgrade

If an upgrade causes problems, you can roll back to the previous version by restoring from your pre-upgrade backup:

./scripts/restore.sh --latest

This restores your database to the pre-upgrade state. Then pull the previous version's Docker images by specifying the version tag:

docker compose pull # Edit docker-compose.yml to specify the previous version tag first # OR use the rollback script: ./scripts/rollback.sh

Contact AegisCore support if you encounter issues during an upgrade or rollback. Do not attempt to manually modify the database to "fix" an upgrade issue — this can cause data corruption that cannot be recovered.

Upgrade Frequency Recommendations

  • Security patches: Apply within 7 days of release. Security patches are backward-compatible and include only fixes, no new features. They are the safest and most urgent updates to apply.
  • Minor version upgrades (e.g., 2.3 to 2.4): Apply within 30 days of release. These include new features, improvements, and non-critical bug fixes. Test on staging first.
  • Major version upgrades (e.g., 2.x to 3.x): Major versions include significant architectural changes and may require manual migration steps. Wait at least 60 days after release for any issues to be discovered and fixed by other users. Read the migration guide carefully. Schedule a maintenance window of at least 2 hours. Contact AegisCore support for assistance with major version upgrades — they are included in your license.
