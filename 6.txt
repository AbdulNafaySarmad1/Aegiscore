SECTION 1 — VOICE & REGISTERS
═══════════════════════════════════════════════════════════════════════════════════

The aegiscore voice has four registers. Switch between them based on context:

  ① INFORMATIONAL  → calm, precise, no filler. State the fact. Stop.
  ② INSTRUCTIONAL  → active verb first, one sentence, tells you exactly what to do and why.
  ③ CELEBRATORY    → warm but not cringe. Human. Brief. Never exclamation marks on system copy.
  ④ CRITICAL/ERROR → never blame the user. Name what broke. Name the fix. That's it.

SECTION 3 — UX MOMENT CLASSIFICATION
═══════════════════════════════════════════════════════════════════════════════════

Every string maps to a UX moment. Apply the matching tone weight per persona:

  IDLE          → minimal copy, let data speak
  LOADING       → honest progress — name exactly what is loading, include dynamic values
  SUCCESS       → brief, specific, named — always include reference number or record name
  WARNING       → name what is at risk + the window to fix it
  ERROR         → name the failure · name the cause · name the action. Three sentences max.
  EMPTY STATE   → invitation + one CTA. Never "No data found."
  ONBOARDING    → conversational, one idea per screen, no walls of text
  CELEBRATION   → warm, specific, non-generic — name what they achieved

SECTION 4 — STAKES CALIBRATION
═══════════════════════════════════════════════════════════════════════════════════

Before writing any string, classify its stakes:

  LOW-STAKES    → casual, brief. Trim ruthlessly.
  MED-STAKES    → precise, scannable. Surface the key noun.
  HIGH-STAKES   → add consequence. Add confirmation. Never shorten.
  IRREVERSIBLE  → mandatory friction. Restate exactly what will be lost.

SECTION 6 — i18n & LOCALE RULES
═══════════════════════════════════════════════════════════════════════════════════

ALL microcopy is an i18n key. Zero hardcoded strings anywhere.

Key pattern:   t('module.context.element.state[.personality]')
Examples:
  t('student.challan.paid.success')
  t('student.challan.paid.success.personality')
  t('finance.gl.journalEntry.post.confirm.highValue')

Every key supports interpolation. All dynamic values are interpolated, never concatenated.
  ✗ "Challan " + challanRef + " verified"
  ✓ t('admin.challan.verified.success', { challanRef, amount, studentName, semesterNumber })

Locale-specific adaptations:
  URDU (ur-PK)   → formal register. "آپ کا" not "تمہارا". Financial terms stay English in parentheses.
  ARABIC (ar)    → Modern Standard Arabic. Numbers via Intl.NumberFormat with ar-SA numeral system.
                   RTL layout — mirror layout only, never mirror meaning.
  ENGLISH (en-PK)→ Pakistani English conventions. "Lacs" not "Lakhs". "Mobile" not "cell".

Currency microcopy:
  Format driven entirely by tenantConfig.currency:
    South Asian:  PKR 1,20,000
    Western:      PKR 120,000
  Never: PKR120000 · Never: 1.2L without context · Never: $ unless tenant currency is USD

Date microcopy:
  Fiscal year: driven by tenantConfig.fiscalYear.startMonth / endMonth. Never assume Jul–Jun.
  Calendar: driven by tenantConfig.calendar ('gregorian' | 'hijri')
  Always show relative + absolute: t('common.date.relativeAbsolute', { relative: '2 days overdue', absolute: date })

The data never changes. The reference number is always there. The amount is always there.

─────────────────────────────────────────────────────────────────────────────────

    Setting: Profile → Preferences → Portal Personality
    Options: t('personality.toggle.off') | t('personality.toggle.on')

TECHNICAL IMPLEMENTATION
─────────────────────────────────────────────────────────────────────────────────

Every i18n key that supports personality has two variants:

  Standard:     t('student.challan.paid.success')
  Personality:  t('student.challan.paid.success.personality')

Selected at render time:
  const key = personalityMode.isActive(userRole)
    ? `${baseKey}.personality`
    : baseKey;
  const copy = t(key, interpolationValues) ?? t(baseKey, interpolationValues);

Missing personality key → fall back to standard silently. Never throw. Never show raw key.

PERSONALITY MODE — ABSOLUTE PROHIBITIONS
─────────────────────────────────────────────────────────────────────────────────

Personality NEVER activates on:
  ✗ Error messages (precision only — always)

SECTION 9 — GRAPH & CHART SYSTEM
═══════════════════════════════════════════════════════════════════════════════════

Every graph in aegiscore must satisfy five laws simultaneously:

LAW A — OMNISCIENT HOVER
  When a user mouses over ANY point on ANY graph, the tooltip must:
  → State the exact value (formatted per tenantConfig.currency and userLocale)
  → State what that value MEANS in context
    (not just "{currency.format(value)}" — "{currency.format(value)} · {percentAboveAverage}% above last month's average")
  → State the trend at that curve segment
  → State any anomaly if present (computed from tenantConfig.analytics.anomalyThresholdSigma)
  → For line segments between points: interpolate and label the trend direction
  This is non-negotiable. A tooltip that only shows the number is a failed tooltip.

LAW B — ZOOM IS NATIVE
  Every time-series graph: scroll wheel, pinch-to-zoom, drag-to-select.
  Zoom resets on double-click or [t('chart.zoom.reset')] button.
  Zoom persists within the session. Navigate away and back = reset.
  On zoom: axes rescale. Gridlines redraw. Data labels reappear at new density.

LAW C — DEVICE OMNIPRESENCE
  Renders correctly at: 375px · 768px · 1280px · 3840px.
  Mobile: touch targets minimum 44×44px. Tooltip above the point, never clipped.
  Mobile: pinch = zoom, tap = tooltip, double-tap = reset.
  Desktop: scroll = zoom, hover = tooltip, click+drag = region zoom, double-click = reset.

LAW D — INTELLIGENT CURVE NARRATION
  Each graph has a one-line insight chip below the title, computed from live data.
  Never hardcoded. Never static.
  Line:   t('chart.insight.line', { trend, percent, period })
  Bar:    t('chart.insight.bar', { topPeriod, percentAboveAverage })
  Donut:  t('chart.insight.donut', { dominantSegment, percent, vsLastYear })
  Area:   t('chart.insight.area', { recoveryPercent, referenceEvent })

LAW E — ACCESSIBILITY IS NOT OPTIONAL
  Every graph: aria-label with full data summary · keyboard navigation ·
  screen-reader-friendly data table toggle · high-contrast mode · prefers-reduced-motion.

CHART TYPE SELECTION — chosen by what the data is SAYING, never by preference:

  How did X change over time?      → Line (single) / Area (filled)
  How do N items compare today?    → Bar (horizontal if names are long)
  What's the part-to-whole split?  → Donut (≤6 slices) / Treemap (>6)
  Where are we vs budget/target?   → Diverging Bar / Bullet Chart
  What's overdue and by how much?  → Waterfall / Stacked Bar Ageing
  How do two variables correlate?  → Scatter (with regression line)
  What's the distribution shape?   → Histogram / Box Plot
  How does performance vary daily? → Heatmap Calendar
  What's the geographic spread?    → D3 Choropleth / Globe (Three.js)
  What's the hierarchy of value?   → Treemap (2D)
  What's a single value vs target? → Gauge / Radial Progress Ring
  What's coming in the next 90d?   → Gantt / Maturity Timeline SVG

FORBIDDEN CHART TYPES:
  ✗ 3D Pie charts — banned globally
  ✗ Dual Y-axis — use two separate charts
  ✗ Radar/Spider charts — use table instead
  ✗ Plain donut with > 7 slices — use treemap
  ✗ Unlabelled axes — every axis has label + unit, always

  ┌────────────────────────────────────────────────────────────┐

#!/bin/sh
set -e

echo "[aegiscore] Deployment mode: ${DEPLOYMENT_MODE:-local}"

# ── 1. Validate required environment variables ────────────────────────────────
REQUIRED_VARS="APP_SECRET DB_HOST DB_NAME DB_USER DB_PASSWORD REDIS_HOST REDIS_PASSWORD"
for VAR in $REQUIRED_VARS; do
  eval VALUE=\$$VAR
  if [ -z "$VALUE" ]; then
    echo "[aegiscore] FATAL: Required environment variable $VAR is not set. Refusing to start."
    exit 1
  fi
done

# ── 2. If DCR enabled, validate DCR variables ────────────────────────────────
if [ "${DCR_ENABLED:-false}" = "true" ]; then
  DCR_REQUIRED="DCR_DB_HOST DCR_DB_NAME DCR_DB_USER DCR_DB_PASSWORD"
  for VAR in $DCR_REQUIRED; do
    eval VALUE=\$$VAR
    if [ -z "$VALUE" ]; then
      echo "[aegiscore] FATAL: DCR_ENABLED=true but $VAR is not set. Refusing to start."
      exit 1
    fi
  done
fi

# ── 3. Wait for primary Postgres ──────────────────────────────────────────────
echo "[aegiscore] Waiting for primary database at ${DB_HOST}:${DB_PORT:-5432}..."
until pg_isready -h "$DB_HOST" -p "${DB_PORT:-5432}" -U "$DB_USER" -q; do
  sleep 2
done
echo "[aegiscore] Primary database ready."

# ── 4. Verify DCR replica reachability ───────────────────────────────────────
if [ "${DCR_ENABLED:-false}" = "true" ]; then
  echo "[aegiscore] Verifying DCR replica at ${DCR_DB_HOST}:${DCR_DB_PORT:-5432}..."
  until pg_isready -h "$DCR_DB_HOST" -p "${DCR_DB_PORT:-5432}" -U "$DCR_DB_USER" -q; do
    sleep 2
  done
  echo "[aegiscore] DCR replica reachable."
fi

# ── 5. Wait for Redis ────────────────────────────────────────────────────────
echo "[aegiscore] Waiting for Redis at ${REDIS_HOST}:${REDIS_PORT:-6379}..."
until redis-cli -h "$REDIS_HOST" -p "${REDIS_PORT:-6379}" -a "$REDIS_PASSWORD" \
  --no-auth-warning ping 2>/dev/null | grep -q PONG; do
  sleep 2
done
echo "[aegiscore] Redis ready."

# ── 6. Run migrations ────────────────────────────────────────────────────────
echo "[aegiscore] Running database migrations..."
npm run migrate:latest
echo "[aegiscore] Migrations complete."

# ── 7. Seed if first boot ────────────────────────────────────────────────────
if [ "${RUN_SEED:-false}" = "true" ]; then
  echo "[aegiscore] Seeding reference data..."
  npm run seed
  echo "[aegiscore] Seed complete."
fi

# ── 8. Start application ─────────────────────────────────────────────────────
echo "[aegiscore] Starting on port ${PORT:-3000}..."
exec node dist/server.js

WAL ARCHIVE SCRIPT (docker/postgres/wal-archive.sh)
─────────────────────────────────────────────────────────────────────────────────

#!/bin/sh
# Called by Postgres archive_command on every WAL segment completion.
# $1 = full WAL file path, $2 = WAL file name
# Uploads to S3-compatible storage. Works with AWS S3, MinIO, GCS via interop, Azure Blob via interop.

set -e

WAL_PATH="$1"
WAL_FILE="$2"
DEST="s3://${WAL_ARCHIVE_BUCKET}/${WAL_ARCHIVE_PREFIX}${WAL_FILE}"

ENDPOINT_ARG=""
if [ -n "${STORAGE_ENDPOINT}" ]; then
  ENDPOINT_ARG="--endpoint-url ${STORAGE_ENDPOINT}"
fi

aws s3 cp "$WAL_PATH" "$DEST" \
  ${ENDPOINT_ARG} \
  --region "${STORAGE_REGION:-us-east-1}" \
  --no-progress \
  --quiet

exit $?

DCR SYSTEM SPECIFICATION
─────────────────────────────────────────────────────────────────────────────────

WHAT DCR COVERS:
  ① Streaming replication    — replica always live, seconds behind primary
  ② WAL archiving            — every transaction archived to object storage
  ③ Automated snapshots      — full base backup on schedule to object storage
  ④ Health monitoring        — primary checked every DCR_FAILOVER_HEALTHCHECK_INTERVAL_S seconds
  ⑤ Failover                 — manual by default, auto if DCR_FAILOVER_AUTO=true
  ⑥ Failover alerting        — POST to DCR_ALERT_WEBHOOK on every failover event
  ⑦ Point-in-time recovery   — restore to any second using base snapshot + WAL replay

RTO (Recovery Time Objective):  < 60 seconds with DCR_FAILOVER_AUTO=true
RPO (Recovery Point Objective): < 5 seconds with streaming replication active
                                 < WAL archive interval with WAL archiving only

FAILOVER SEQUENCE:
  1. Health monitor detects primary unreachable after DCR_FAILOVER_THRESHOLD_FAILURES checks
  2. POST alert to DCR_ALERT_WEBHOOK:
     { event: 'primary_unreachable', timestamp, lastHealthy, replicaLagSeconds }
  3a. If DCR_FAILOVER_AUTO=true:
       → pg_promote() on replica
       → DB_HOST updated in runtime config to DCR_DB_HOST
       → All pool connections reconnected to new primary
       → POST: { event: 'failover_complete', newPrimary, rto, rpo }
  3b. If DCR_FAILOVER_AUTO=false:
       → POST: { event: 'manual_failover_required', instructions }
       → App continues serving read traffic from replica

POINT-IN-TIME RECOVERY PROCEDURE:
  1. Identify target recovery timestamp
  2. Restore latest base snapshot from DCR_SNAPSHOT_BUCKET to a new Postgres instance
  3. Apply WAL files from DCR_WAL_ARCHIVE_BUCKET up to target timestamp
  4. Promote the recovered instance
  5. Point DB_HOST to recovered instance
  6. Run: npm run db:verify
